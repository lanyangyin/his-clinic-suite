# 标准对照与差距（2026-11）

> 详细逐项版见：[标准逐条对照（详细版）](标准逐条对照.md)；本文保留摘要。

## 口径

这份审计不追求“功能越多越像医院”，只回答三个问题：

1. 当前模块在《全国医院信息化建设标准与规范（试行）》的功能框架里处于什么位置。
2. 以电子病历系统应用水平分级 3/4 级为务实目标，哪些闭环还缺关键字段/状态。
3. 哪些开源项目的设计值得参考，哪些不能直接照搬。

官方文件只取目录、功能分类和分级要求，不逐条抄全文；具体条款以原文为准。

## 当前模块位置

当前后端约 60 个业务包、57 个路由入口，已经不是“单表门诊”，但仍然是**门诊交易闭环**，不是全院级 HIS。

可以粗分为：

| 标准框架中的位置 | 当前模块 |
|---|---|
| 患者与便民服务 | patient、registration、appointment、triage、portal、kiosk、sms |
| 门急诊医疗 | encounter、lis、pacs、treatment、treatment_room、tcm、surgery |
| 药品与药事 | drug、pharmacy、warehouse、materials、gsp |
| 费用与结算 | billing、charges、cashier、invoice、insurance、finance |
| 护理与执行 | nursing、treatment_room、cssd |
| 病案与质量 | archive、review、pathway、reports、bi |
| 运营与人事 | hr、staff、performance、admin |
| 接口与安全 | integration、ca、auth、idempotency、download |

结论：

- **框架位置基本齐全**，不需要为了“像医院”再加大量空模块。
- 真正的短板在**临床核心的闭环和证据链**，不在模块数量。

## 电子病历 3/4 级视角的差距

不把“有页面”当成“达到级别”。按 3/4 级最相关的闭环看：

### 1. 处方头与处方类型

2026-11-22 后：

- 已有 `prescriptions` 处方头与 `prescription_items.prescription_id`
- 已有处方号/类型/状态
- 5 种上限已改为按处方头
- 旧数据已回填 `RXLEGACY...`，并标记 approved

差距：

- 无法按“一张处方”审方、打印、上传医保
- 无法区分普通西药/中成药、中药饮片、麻精、慢特病等
- 无法记录处方级审核/退回/作废

优先级：**P0**

### 2. 药事审方与用药闭环

当前：

- 有发药、退药、取药码、发药队列、发药核对
- 有过敏硬拦截、相互作用规则、特殊级抗菌药拦截
- 没有独立“药师审方”状态机
- `Dispense` 是一次就诊一条，没有按明细记录实际发药

差距：

- 处方生成后没有“待审方 → 通过/退回 → 调配 → 发药”闭环
- 发药凭证只能按处方明细聚合，不能证明实际发了哪些批次/数量
- 麻醉/第一类精神药品没有专用处方和处方权

优先级：**P0/P1**

### 3. 病历修改留痕

当前：

- 病历可保存、签名、质控评分
- 诊断支持编码+名称，但常用字典规模有限
- 病历修改没有独立的版本/审计表

差距：

- 签名后修改的痕迹、修改人、修改原因不足
- 诊断未接完整 ICD 目录/医保诊断目录
- 电子病历分级看的是“可追溯”，不只是“能保存”

优先级：**P0/P1**

### 4. 医嘱执行闭环

当前：

- 检验、检查、治疗、护理执行各有状态
- 注射/输液执行单没有从药品处方明细自动派生
- 护理核对有高危药双人核对基础，但缺少腕带/扫码闭环

差距：

- 处方 → 审方 → 调配 → 发药 → 执行，不是一条可追溯链
- 执行单与处方明细的关联需要显式字段

优先级：**P1**

### 5. 数据共享与接口

当前：

- 有 LIS/PACS 模型和报告回传
- 有 integration/download 模块
- 真实医保、LIS、PACS 接口仍需按部署环境接入

差距：

- 分级评价强调院内数据共享和闭环，不是单机页面
- 需要明确接口边界、失败重试、审计

优先级：**P1**

## 智慧服务视角

当前已有：

- 预约、挂号、收费、取药码、报告查询、门户、自助机、短信
- 取药凭证、打印预览

差距：

- 患者端在线支付/报告/排队实时状态还不完整
- 没有统一患者门户账号体系
- 没有互联网医院/随访的完整闭环

优先级：**P2**，不应先于临床核心。

## 开源项目怎么用

参考 OpenHIS 和其他 Gitee HIS 项目时，只看三样：

1. README 的模块边界
2. 数据库表结构：患者、就诊、处方头、医嘱、执行、费用如何关联
3. 状态机：处方、检验、检查、治疗、发药分别有哪些状态

不直接复制代码，原因：

- 技术栈不同（Spring Boot/Vue3 vs FastAPI/PySide6）
- 大医院流程和小诊所流程不同
- 直接搬表结构会把当前系统拖进不必要的复杂度

## 建议的下一轮

### P0：临床核心

1. ✅ `prescriptions` 处方头 + `prescription_id`
2. ⚠️ 处方类型：普通西药/中成药、中药饮片、麻精（麻精仍缺）
3. ✅ 5 种限制改为按处方头
4. ✅ 药师审方状态机（西药/中成药）
5. ✅ 病历修改留痕
6. ✅ 患者访问审计（谁看了哪个患者）

### P1：执行与共享

1. 注射/输液执行单从处方明细派生
2. `dispense_items` 实际发药明细
3. LIS/PACS 接口状态与失败重试
4. 医保患者类型进入结算

### P2：智慧服务

1. 患者门户账号
2. 在线支付/报告/排队
3. 随访/互联网医院

## 当前不做

- 为了评级堆砌住院、手术、ICU、DRG 模块
- 没有真实接口就宣称“已接入医保/LIS/PACS”
- 把官方规范全文照抄成功能清单

## 结论

当前系统是一个**门诊交易闭环完整、临床证据链仍偏薄**的系统。

下一步最值得做的不是再加页面，而是：

```text
处方头 → 审方 → 调配 → 发药 → 执行
病历修改留痕
患者访问审计
```

这三条补上，才更接近电子病历 3/4 级所要求的“可追溯闭环”。
