## 逐模块结论

### archive（P0 / optimize_now）

归档状态机与“院长审批+双人执行+清册打印”是本批最完整闭环；但同一模块并存旧销毁接口，病案管理员凭自由文本审批人即可置 destroyed，绕过院长审批且不可逆；复印费也不进收费系统。

**发现：**
- 销毁审批绕过（不可逆）：app/modules/archive/router.py:189-200 POST /archive/records/{id}/destroy 仅 require_role('archive')，service.py:231-252 destroy_record 只校验 approved_by 非空即置 destroyed，不查 ArchiveDestructionRequest；管理台同样暴露 POST /admin/archive/records/{id}/destroy（app/modules/admin/router.py:1794-1816）。
- 绕过已被测试固化：tests/test_archive.py:120-128 以 approved_by='医务科' 直接销毁并断言 200/status=destroyed；docs/院长审批工作站.md:38 明示“旧接口保留兼容”。
- 新流程达标（保留）：service.py:278-318 限 archived/draft、借出中禁止、同病案不得重复未完成申请；router.py:235-260 批准仅 director；service.py:362-393 执行要求 witness≠operator 并写 ArchiveDestruction 清册；router.py:327-367 清册打印做 HTML escape。
- 复印费不入账：ArchiveCopyRequest.fee（models.py:81）仅在 complete_copy（service.py:170-184）写值，全仓库无 EncounterCharge/Payment 关联 → 复印收费不产生收费记录、不进日结、不开票。
- 借阅无审批无逾期：service.py:107-128 borrow_record 将 approver 直接置为操作人；models.py:63-64 定义 overdue 但无代码置位，list/history 无逾期扫描。
- 页数为手工录入（service.py:85-104），与病历实际页数、completeness 无数据源关联；archive_no 由 BA+日期+自增 id 生成（service.py:31-33），唯一约束在列上（models.py:15）。
- 附件：后缀白名单+10MB（router.py:294-299），uuid 文件名落 data/archive_destructions，下载限 archive/director/admin（router.py:310-315）；无病毒扫描、无水印、无下载留痕。
- 客户端：his_client/ui/archive.py 覆盖建档/归档/借阅/复印/封存/销毁申请/执行/打印，但 _refresh_borrow 借阅人/应还日期两列恒空（archive.py:354-361），复印完成（fee）无入口；his_client/api.py:549-550 destroy_archive 为无 UI 调用的死代码。
- 测试：tests/test_archive.py(3)+tests/test_director_approvals.py(4) 覆盖全生命周期、完整性拦截、职责分离、驳回后重新申请；未覆盖并发 archive_no、复印费入账、逾期置位。

**标准依据：** EMR-2018-1079 第32项 病历管理/电子病历文档应用（授权浏览、留痕）；EMR-2018-1079 第31项 病历管理/病历质量控制（整改闭环）；NHC-2018-4 第(46)项 电子病历质量管理（当前仅表单完整性检查）；NHC-2018-4 第(73)项 业务结算与收费（复印费未入收费/日结）

### auth（P0 / optimize_now）

口令哈希与幂等中间件扎实，但两个数据接口完全无鉴权、审计缺 IP/GET 留痕、管理台会话签名密钥有公开缺省值且管理台写操作在审计表记为 anonymous，是本批最高优先级安全问题。

**发现：**
- app/modules/auth/router.py:43-48 GET /users/{user_id} 无任何鉴权依赖，未登录即可按 ID 枚举用户名/角色/employee_id/doctor_id/narcotic_right。
- app/modules/auth/router.py:67-69 GET /audit/logs 无任何鉴权依赖，未登录可读全量审计日志；tests/test_auth.py 只断言写接口 401/403，未覆盖这两个读接口。
- app/modules/auth/security.py:49-65 require_role 内置 admin 恒通过；权限模型仅 User.role 单字符串（app/modules/auth/models.py:8-20），无角色-权限表、无科室/本人数据范围。
- app/migrate.py:38-76 部署时写入固定口令 admin/admin123 与 director/director123，User 无 must_change_password 字段，schemas.UserCreate 无密码长度/复杂度校验。
- app/settings.py:47-50 SECRET_KEY 缺省回退 'his-dev-secret-change-me-0123456789'，app/main.py:255 用它签名管理台 SessionMiddleware Cookie；未注入 HIS_SECRET_KEY 即可伪造管理台会话，启动不校验不拒启。
- app/main.py:178-191 审计中间件只对 POST/PUT/PATCH/DELETE 记 method+path+status_code，无 IP、查询参数、请求体、患者标识；敏感 GET（报表/驾驶舱/日结/审计日志）不留痕。
- app/modules/admin/router.py:247-256 _guard 未写 request.state.user_name，app/main.py:183-190 只读该字段 → 管理台 101 处守卫下的写操作在 audit_logs 记为 anonymous，审计归属断裂。
- app/modules/auth/models.py:23-34 AuditLog 无 ip/patient_id/query/biz_id；跨模块 app/modules/patient/models.py:87-102 PatientAccessLog 亦无 ip，与 docs/标准逐条对照.md P0-4 验收项（含 ip）不符。
- HTTP Basic（security.py:10）+ 默认 HOST=0.0.0.0（app/settings.py:45）且应用层无 TLS；无会话超时、无多因素、无登录失败锁定/限速，凭据在局域网明文。

### catalog_proposal（P1 / optimize_now）

- 提交端不查重：`create_proposal` 不检查同名/同规格是否已有 Drug 或 ChargeItem、也不检查是否已有同名的在途建议（[catalog_proposal/service.py:15](app/modules/catalog_proposal/service.py#L15)）；只在最终审批时按 Drug.name（[catalog_proposal/service.py:131](app/modules/catalog_proposal/service.py#L131)）或 ChargeItem.code（[catalog_proposal/service.py:153](app/modules/catalog_proposal/service.py#L153)）拒绝，导致重复建议可以把整套审批走完再失败；且同名不同规格无法表达（Drug 唯一性只按 name 判定）。

### nursing（P1 / optimize_now）

门诊输液/注射执行链较完整：审方后从处方明细按 route 关键词派生执行单、配药/核对/开始/巡视/完成/跳过、高危药第二核对人校验、执行单唯一来源约束、输液标签打印都有实现。但执行前不校验收费/发药、第二核对人只是自由文本、效期不校验、完成覆盖执行人、不良反应停药写入非标准状态，且不覆盖住院护理记录。

**发现：**
- 执行前无收费/发药门禁：sync/prepare/start 均不检查 Payment 或 Dispense（app/modules/nursing/service.py:32-105、161-207），已审方但未收费、未发药的处方即可配药执行；对照 pharmacy 发药要求 payment.status == paid（app/modules/pharmacy/service.py:107-109）。
- 高危核对人不可信：prepare 仅比较 checked_by 字符串与 operator（service.py:169-174），不校验其为存在的护士账号、不要求第二人独立登录；docs/高危药品双人核对.md 的“边界”自认“不是第二人独立登录/电子签名”。
- 效期不校验：prepare 记录 expires_at（service.py:182），start 不检查是否过期（service.py:194-207），过期药液仍可执行。
- 执行人覆盖：complete 把 executed_by 覆盖为完成人（service.py:243-247），丢失 start 时的执行人；NHC（30）/EMR #8 要求执行可追踪到人，应分 started_by/completed_by。
- 非标准状态 stopped：encounter.service.record_adverse_reaction 把 NursingOrder.status 置为 stopped（app/modules/encounter/service.py:1426-1428），但 nursing 模型声明的状态只有 pending/prepared/executing/completed/skipped（models.py:33）；skip/complete 都会拒绝该状态，药物反应停药后的执行单无法正常收尾。docs/诊疗状态与药物反应.md:31 记录了这个行为。
- 并发无原子更新：prepare/start/complete 都是读-改-写（service.py:161-250），没有像 treatment.execute 那样做条件 UPDATE；nursing_preparations 也没有 order_id 唯一约束，并发可重复配药。
- 不回写治疗单：nursing 从 TreatmentOrder 派生执行单（service.py:73-104），但完成/跳过不回写 TreatmentOrder，治疗单仍 pending，可与 /treatments/{id}/execute 形成双执行源。
- 无住院护理记录：本模块只有 NursingOrder/NursingPreparation/NursingObservation（models.py 全部模型），没有护理记录、评估、体温单、护理级别、不良事件；住院执行在 inpatient 模块另有 OrderExecution（app/modules/inpatient/models.py:77-85），两者无关联。docs/标准逐条对照.md #9 称“有护理记录基础”，与 nursing 包不符。
- 无患者身份核对/腕带扫码：start/observe/complete 均无患者标识、腕带、条码字段（service.py:194-250），NHC（29）（30）要求的身份确认缺失。
- 无访问审计与打印鉴权：模块不调用 record_access；GET /print/nursing-label/{order_id} 无任何鉴权（app/modules/print/router.py），可按 ID 枚举输液标签。
- 测试/客户端/管理台：tests/test_nursing.py 2 + test_high_alert_nursing.py 2 共 4 个用例，覆盖主流程与高危核对；客户端 his_client/ui/nurse.py 覆盖执行单流程；管理台无护理页面。收费/发药门禁、过期、并发、执行人覆盖、stopped 状态均无用例。

**标准依据：** NHC-2018-4（28）护理记录；NHC-2018-4（29）非药品医嘱执行；NHC-2018-4（30）药品医嘱执行；NHC-2018-4（31）输液管理；NHC-2018-4（32）护理信息提醒；NHC-2018-4（50）护理质量管理；EMR 3/4级 #8 病房护士医嘱执行、#9 病房护士护理记录

**参考工程：** reference/comparison.md §3.2 发药明细（执行明细应有数量/批号/执行人）；reference/comparison.md §4 状态机（处方/执行状态分层）；reference/comparison.md §5 值得借鉴（发药明细与执行闭环）；reference/README.md 对照结论

**建议：** 增加“已收费且已发药”执行门禁；高危核对人改为从用户表选择或扫码独立登录，并记录双签；start 校验 expires_at；执行人拆分为 started_by/completed_by；把 stopped 纳入护理状态机并允许收尾；补护理记录/评估并明确与住院 OrderExecution 的边界；补 record_access 与打印鉴权。

**不优化理由：** 不能延后：未收费/未发药即可执行输液是收费与用药安全的双重漏洞；高危“第二核对人”可任意填名字使其形同虚设；停药状态 stopped 不在护理状态机内，会让执行单永久挂起。这些直接影响用药安全与收费闭环。

### pacs（P1 / optimize_now）

影像检查只有 pending→reported 两态，报告无报告人、无审核、无结构化模板，图像只有一个 image_url 字符串，字典无管理台页面；读接口未鉴权。属于“有申请单和报告文本”的起步实现，不能视为 PACS/RIS 已接入，但报告文本与图像 URL 已进入临床使用。

**发现：**
- 状态机仅 pending/reported：ImagingRequest 注释与默认值只有两态（app/modules/pacs/models.py:32-33），report_request 只允许 pending 转 reported（service.py:97-98），无预约/登记/检查中/报告审核/退回/取消；docs/取药凭证与医技单据.md 的“当前缺口”明确承认检查状态机比检验短。
- 报告无报告人/审核：ImagingRequest 没有 reported_by/reviewed_by 字段（models.py:19-40），report_request 不接收操作者（service.py:90-108），router 用 _ 丢弃用户（router.py:96-104）；影像报告无法追到写报告的人。
- 无图像/真实接口：image_url 为 String(200)（models.py:40），无 DICOM Study/Series、无 PACS 调阅、无接口失败重试与审计；docs/标准逐条对照.md（36）明确“不能把 image_url 当成 PACS 已接入”。
- 未鉴权读取影像报告：GET /pacs/items/、/pacs/items/{id}、/pacs/encounters/{id}/imaging-requests、/pacs/requests/{id} 无鉴权（router.py:40-93），报告文本与 image_url 可按 ID 枚举；tests/test_pacs.py:163-165 匿名请求可直达路由并返回 404（而非 401）。
- 无预约/排期/资源：ImagingItem 只有 code/name/body_part/price（models.py:9-16），无 modality、无检查室、无时段/预约；NHC（36）与 EMR #16 的申请与预约能力未实现。
- 计费口径不一致：ImagingItem 无 insurance_ratio 字段，create_request 硬编码 insurance_ratio=0.7（service.py:58-69），与 LIS 按项目比例、治疗按 ChargeItem 比例不一致，医保结算会出现偏差。
- 字典无管理台页面：app/modules/admin/router.py 路由清单无 imaging 项目维护页，admin 模板也无对应页面，只能调 admin API 建检查项目；医生端 doctor.py 可选择下单，但字典维护入口缺失。
- 无报告危急值/结构化/审核：ImagingReportRequest 只有 report + image_url（schemas.py:22-24），无 critical、无模板、无审核状态，NHC（36）与 EMR #18 的结构化报告/审核要求未落地。
- 重复下单无幂等：同一 encounter/item 可反复申请，每次各自计费（service.py:35-73），无唯一约束或业务幂等键，双击可重复开单/重复收费。
- 测试/客户端/管理台：tests/test_pacs.py 12 个用例覆盖建项/申请/报告/唯一 accession/权限；客户端 his_client/ui/radiology.py 只有工作列表与写报告两个动作，无预约/审核/图像；管理台无 PACS 页面。匿名可读、无报告人、无审核均无用例。

**标准依据：** NHC-2018-4（36）医学影像信息管理；EMR 3/4级 #13 门诊检查申请、#14 门诊检查报告、#16 检查科室申请与预约、#17 检查记录、#18 检查报告、#19 检查图像；智慧服务 #4 诊中信息推送

**参考工程：** reference/comparison.md §3.5 LIS/PACS 字段对照；reference/comparison.md §4 状态机（检查状态应分层）；reference/comparison.md §6 证据索引（app/modules/pacs/models.py）；reference/README.md 对照结论

**建议：** 优先与 LIS 同批做安全修复：给 /pacs/encounters/{id}/imaging-requests、/pacs/requests/{id}、/pacs/items 加鉴权；补 reported_by、报告审核/退回状态与结构化报告；为 ImagingItem 增加 insurance_ratio/modality，并新增 admin 影像项目页面；在决定是否接 DICOM/PACS 前，界面与文档必须标注“未接入真实 PACS”，image_url 只能作为外部链接占位。

**不优化理由：** 读接口未鉴权与 LIS 同属患者报告泄露，应并入同一 P0 安全批次；但模块本身无图像接口、预约、报告审核，完整 PACS 依赖外部系统，故模块整体列 P1 优化，而不是把外部接口工程误标为 P0。

### payment_gateway（P1 / optimize_now）

支付通道是“未配置即模拟成功”：现金直接成功，微信/支付宝/POS/医保卡未启用或未填网关时返回 success/mock，但收费层仍写 Payment(status=paid)、关闭就诊、占用发票号，日结与报表按真实收入统计。配置后走 HTTPS+HMAC，但只校验回执 code、不验签；退款请求连签名头都不带，混合支付退款还传空交易号。属资金链路高风险实现。

**发现：**
- 默认模拟成功且污染收入数据：service.charge（app/modules/payment_gateway/service.py:144-151）未配置时返回 success/mock；billing.service.create_payment 照常写 Payment(status=paid)、charge.status=paid、close_encounter、allocate 发票号、生成取药码（app/modules/billing/service.py:142-181）。
- 回执不验签：charge 只判断 body.code/success（service.py:222-231），未校验网关响应签名；refund（service.py:234-271）只发 Content-Type、不带 X-Sign、不校验回执，内网网关或中间人可伪造“支付成功/退款成功”。
- 混合支付退款断链：billing.service.refund_payment（app/modules/billing/service.py:274-293）按分渠道调用 refund(db, allocation.channel, "", part)，trade_no 传空；payment_gateway.refund 对 channel=="mixed" 直接返回模拟成功（service.py:240-241）。
- 密钥/证书明文：models.PaymentChannelConfig.api_secret 明文入库（models.py:31-33），仅页面掩码（service.py:96-99）；gateway_url 允许 http，无 TLS 强制。
- 医保卡只有卡号字段：charge 对 insurance_card 仅校验 card_no 非空（service.py:160-166），无读卡器/PSAM/医保授权（docs/入库与医保目录设计.md §二十 已声明模拟）。
- 无独立 REST 路由：配置只在管理台会话内（app/modules/admin/router.py:1029-1081，_guard 校验 admin session），第三方终端无法安全读写；覆盖：tests/test_payment_gateway.py 9 例 + test_mixed_payment.py + test_partial_refund.py，客户端收费面板走 /payments（his_client/ui/payment.py、cashier.py）。

**标准依据：** NHC 2018-4 第10项 支付方式（✅：现金/微信/支付宝/POS/医保卡）；NHC 2018-4 第73项 业务结算与收费（⚠️：医保是 Mock，不能宣称合规）；NHC 2018-4 第9项 便民结算（⚠️：有窗口/诊间收费，无床旁/移动结算）；医院智慧服务 2019-236 第12项 费用支付（3级：窗口移动支付；⚠️）

**参考工程：** docs/入库与医保目录设计.md §二十 收费支付通道、§二十二 按明细/按数量退费（含“医保只能整单退”）；docs/标准逐条对照.md §4.1（10）（73）；reference/comparison.md、reference/README.md 未覆盖支付通道

**建议：** 1) 增加“生产模式”开关，生产禁止静默 Mock 成功，未配置直接拒绝并在收据标注；2) charge/refund 双向签名与验签，退款必须带原 channel_trade_no；3) 收款时把每笔分渠道 trade_no 写入 payment_allocations（表已有字段但 create_payment 未写），退款按 allocation.trade_no 调用；4) 密钥加密存储或托管，强制 https。

**不优化理由：** 不适用：判定为本轮整改。资金类回调不验签、退款不签名、模拟成功计入真实收入，都是上线前必须消除的风险。

### publichealth（P1 / optimize_now）

传染病报告只有“草稿→已上报”两张状态和 6 个业务字段，无报告卡要素（分类/发病日期/诊断日期/报告单位/订正/死亡）、无区域平台接口/回执/重试、无客户端或管理台页面，且列表/详情未鉴权；submit 的 docstring 自认是“模拟上报”。属于不可用于真实上报的占位实现，但 NHC（62）是法定上报能力，不能简单删除。

**发现：**
- 报告卡字段缺失：DiseaseReport 只有 encounter_id/disease_code/disease_name/status/reported_by/submitted_at 等业务字段（app/modules/publichealth/models.py:8-27），无法定传染病报告卡的甲/乙/丙分类、发病日期、诊断日期、报告单位、订正/死亡/转归等要素。
- 上报是模拟且无回执：submit_report 只把 status 置 submitted、写 submitted_at（service.py:53-65），docstring 明确“上报区域平台（模拟）”；无平台 URL/报文/回执/失败重试/接口日志；docs/标准逐条对照.md（62）为 ❌。
- 无订正/作废/删除：router 只有 create/list/get/submit（router.py 全部端点），报告错误无法订正或作废，也没有报告卡编号。
- 未鉴权读取：GET /public-health/reports、/reports/{id} 无鉴权（router.py:26-36），可按 encounter_id 枚举传染病病种与上报状态；tests/test_publichealth.py:89-95 以匿名 GET 断言 200。
- 上报权限错位：submit 仅 admin（router.py:39-46），临床医生/防保人员不能上报；创建仅 doctor（router.py:13-23），没有防保科审核环节。
- 去重范围有限：唯一约束仅 (encounter_id, disease_code)（models.py:25-27），同一患者多次就诊/多张报告卡可重复，无患者维度去重。
- 无客户端/管理台入口：his_client/ui/main_window.py 无公卫页面，app/modules/admin/router.py 无公卫页面；只有 API 与 tests/test_publichealth.py 7 个用例。
- 无时限/预警联动：没有上报时限提醒、传染病预警、隔离提示与门诊病历/分诊的联动（service.py 全文件）。
- 测试：7 个用例覆盖创建/重复/提交/列表/权限，但未覆盖报告卡字段、接口回执、订正、未鉴权读取。

**标准依据：** NHC-2018-4（62）传染病信息上报；NHC-2018-4（58）院感管理（传染病预警联动，当前无）

**参考工程：** reference/comparison.md §2 模块边界（未覆盖公卫）；reference/comparison.md §5 不直接借鉴区域协同模块；reference/README.md 对照结论

**建议：** 先补最小合规闭环：报告卡要素（分类、发病/诊断日期、报告单位/医生、订正/死亡/转归）、订正与作废状态、上报回执/失败重试、患者维度去重、防保角色与审核；给读接口加鉴权，增加客户端/管理台入口和上报时限提醒。若机构实际使用区域平台直报，则明确 deprecate 本模块并保留导入/留痕，不要维持半套实现。

**不优化理由：** 不能按 keep 处理：法定传染病上报是合规硬要求，当前既无报告卡要素也无接口回执，无法用于真实上报；但完整对接区域平台依赖外部环境，故先做最小合规闭环（字段+订正+回执+鉴权+入口），列 P1 而非 P0。

### receiving（P1 / optimize_now）

入库单收货→验收→入库状态机、药品批号/效期与器械注册证强校验、不合格数量与拒收原因、入总库并记流水都是真实实现；但事务不原子、与 GSP 验收和采购申请脱节、可绕开采购直接入账、列表接口匿名可读。

**发现：**
- 状态机与校验完整：received→checked→stocked/cancelled 均有状态判断；_build_items 强制药品批号+有效期、器械注册证号（service.py:25-107）；check_order 登记 rejected_qty/reject_reason，stock_order 只入合格数量。
- stock_order 非原子且中途提交：materials.service.stock_in 即使 record=False 仍 db.commit()（materials/service.py:70），药品行先改 WarehouseStock 再遇后续报错会留下已提交库存；order.status 无原子条件更新，并发两次 /inbound/orders/{id}/stock 可重复入库。
- 与 GSP 验收重复且未打通：gsp.GspAcceptance 用自由文本 drug name/supplier_name 独立建表（gsp/models.py），receiving 既不创建也不引用 GSP 验收记录；同一到货可只做 receiving 验收，GSP 记录可完全缺失，验收结论双轨。
- 与采购申请/采购单无关联：InboundOrder 无 purchase_request_id/采购单号字段（models.py），warehouse 角色可直接建任意数量入库单入总库，supplier_id 可空且不校验供应商资质（schemas.py:33-40），入库缺少前置审批依据。
- cancel_order 无取消人/取消时间字段，审计只靠全局中间件；而 admin 会话写操作在审计中间件里记为 anonymous（admin 只设 request.session，不设 request.state.user_name）。

### treatment（P1 / optimize_now）

门诊治疗单（医生开单即计费、护士执行）主链可用，pending→done/cancelled 的状态推进使用条件 UPDATE 做原子更新，这一点比同批多数模块好。但取消直接把费用置 refunded、绕过 billing 的退款单/支付冲正/日结，执行无核对人/批号，读接口未鉴权，且与 nursing、treatment_room 两套执行路径没有打通。

**发现：**
- 取消绕过收费退费：cancel_treatment 直接把 EncounterCharge.status 置为 refunded（app/modules/treatment/service.py:109-124），不生成 ChargeRefund、不改 Payment、不写退款渠道/操作者；合规退费在 billing.refund_payment（app/modules/billing/service.py:212-340），该路径绕开收费员日结；tests/test_treatment.py:98-113 固化了“无退款单也变 refunded”。
- 已收费后仍可取消：cancel 不检查 encounter.status 是否 closed、也不检查 charge.status 是否 paid（service.py:109-124），可在收费完成后把费用改成 refunded，造成账实不符；若该模块已真实收费，此条应升 P0。
- 执行无证据链：execute_treatment 只写 executed_by/executed_at（service.py:82-106），无核对人、无批号、无皮试/过敏复核、无执行备注；NHC（29）（31）要求的身份确认与核对未体现。
- 未鉴权读取：GET /treatments/、/treatments/encounters/{id}、/treatments/{id} 无鉴权（router.py:20-55），治疗单与就诊关联可被枚举；tests/test_treatment.py:122 匿名读取 200。
- 与护理执行重复：nursing 会从 pending TreatmentOrder 派生执行单（app/modules/nursing/service.py:73-104），但 nursing 完成不回写 TreatmentOrder.status，治疗单仍是 pending，随后仍可调 /treatments/{id}/execute，形成两条执行记录。
- 与治疗室无强关联：treatment_room_cases.treatment_order_id 只是裸 Integer、无外键（app/modules/treatment_room/models.py:27），create_case 不校验该治疗单存在/归属，实际没有消费治疗单。
- 无幂等/唯一约束：同一 encounter/item 可反复开单，无业务幂等键；只有费用按 source_type+source_id 去重（charges/service.py:53-66），治疗单本身不去重。
- 计费口径：使用 ChargeItem.insurance_ratio（service.py:41-52），口径正确；但取消后没有耗材/药品回退联动，也没有库存流水冲销。
- 测试/客户端/管理台：tests/test_treatment.py 9 个用例覆盖开单/执行/取消/权限；客户端无独立治疗单页，只在护士站“待执行治疗”使用（his_client/ui/nurse.py 调 list_pending_treatments/execute_treatment）；管理台无治疗单页面。取消退款、已收费取消、双执行路径均无用例。

**标准依据：** NHC-2018-4（23）门急诊处方和处置管理；NHC-2018-4（29）非药品医嘱执行；NHC-2018-4（31）输液管理；EMR 3/4级 #23 治疗信息处理/一般治疗记录

**参考工程：** reference/comparison.md §4 状态机（处方/发药分层，执行应有独立记录）；reference/comparison.md §5 值得借鉴（审方、发药明细、执行闭环）；reference/README.md 对照结论

**建议：** 取消治疗单必须走 billing.refund_payment，生成退款单、支付冲正并在收费日结可见；取消前校验 encounter.closed 与 charge.paid；执行单补核对人、批号、皮试/过敏复核；给读接口加鉴权；明确 treatment、nursing、treatment_room 的单一执行源：要么治疗室/护理消费治疗单并回写状态，要么删除重复路径。

### warehouse（P1 / optimize_now）

总库→药房/科室的出库单状态机（submitted→approved→partially_issued→issued/cancelled）、按角色分单类型、FEFO 分配、盘点调整、采购申请审批链都是真实实现，是库存侧最完整的模块；主要缺陷在并发/事务边界、结存字段准确性与操作人留痕。

**发现：**
- 结存可能记旧值：_issue_drug_fefo 先 query 全部批次（进 identity map），再 update(synchronize_session=False)，随后 record_drug→stock_ledger._drug_balance 重新 query 同一批对象不会刷新 → balance_after 记的是扣减前数量。已用 SQLAlchemy 复现：不 expire 读到 10，expire 后为 4；对照 pharmacy.deduct_stock 显式 db.expire(stock)，warehouse 的 _deduct_drug/_issue_drug_fefo 都没有 expire。该 balance_after 被 insurance_inventory.build_records 直接上传医保进销存。
- transfer 未传操作人：router.py:80-89 调 transfer(db,data) 未带 user.username，库存流水 operator 为空；transfer 还是读-改-写（wh.quantity -=），无 条件 UPDATE，并发可超发、新建药房批次可撞 uq_drug_stocks_drug_batch 直接 500。
- purchase 读-改-写 + get-or-create，无 IntegrityError 兜底（对比 pharmacy.dispense 有唯一键兜底）；单号用 max(id)+1（create_outbound / _next_purchase_request_no），并发重号撞唯一键。
- approve_outbound/cancel_outbound 非原子（先查 status 再赋值）；cancel 允许 partially_issued 取消，已出库部分不回滚、不记取消人。
- receive_purchase_request 逐条调用 purchase()，而 purchase 内部 db.commit()（service.py:553）→ 部分到货中途失败会留下已提交行，整单事务被拆碎。
- warehouse.check 单批次盘库直接改库存并生成 StockAdjustment，无第二人复核；与 stocktake 模块并行两套盘点机制。
- 采购申请审批虽调用 approval.advance_request，但业务路由 approve_purchase_request 只校验 admin/director，不校验当前步骤 role_required（只有 /approvals/requests/action 校验 step role，approval/router.py:136-141）。
- GET /purchases、/stocks、/checks、/outbound-orders、/outbound-orders/{id} 无鉴权（router.py:66-146），泄露供应商、采购与单据明细。

**标准依据：** NHC 2018-4（56）药物物流管理（docs/标准逐条对照.md L190）；NHC 2018-4（82）临床试剂（L216）、（83）高值耗材管理（L217）、（84）低值耗材及办公用品（L218）；医保进销存上传依赖本模块流水（docs/入库与医保目录设计.md L32、L112）；电子病历第 29 项 门诊药品调剂（L70）

**参考工程：** 上海哲策 DmSstore.java：upLimit/downLimit/realNumber/lostNumber/backNumber/isExpired/batchId/storeId/sellPrice；上海哲策 McSinDO.java：billCode/provider/auditor/inType/rStoreId/sStoreId/storeNumber（耗材入库单）；OpenHIS InventoryItem.java：locationStoreId/locationId/lotNumber/expirationDate/traceNo；workflow/domain/SupplyRequest.java + SupplyDelivery.java 的请领-配送工作流

**建议：** 出库/调拨/采购改为条件 UPDATE + 记账后 expire 或 re-select 结存；transfer 传 operator；单号改独立计数表/序列并捕获 IntegrityError 重试；取消加「已出库禁止」与 cancelled_by；receive 用单事务（purchase 提供 commit=False）；把 warehouse.check 并入 stocktake 盘点单；业务审批统一走 /approvals/requests/action 的步骤校验；GET 全部补 require_role。

### admin（P2 / optimize_later）

- 双仪表盘：/admin（router.py:300-313 + dashboard.html + admin/service.py:16-53）与 /admin/dashboard（router.py:2653-2728 + operations_dashboard.html，聚合内联）同一看板两套代码。

### idempotency（P2 / optimize_later）

幂等中间件方向正确（唯一约束原子占位→执行→缓存响应→并发 409→5xx 释放），测试覆盖原子性、重放、endpoint 隔离、业务错误缓存。但缓存键只有 (key, endpoint)、没有用户维度：两个用户用同一 Idempotency-Key 命中同一端点时，后者会拿到前者缓存的响应体（可能含患者数据）；另外无 TTL 清理、processing 残留永久 409、4xx 也被永久缓存，中间件还全量缓冲响应。当前没有任何客户端发送该头，缺陷尚未被真实流量触发。

**发现：**
- 幂等键不区分用户：IdempotencyKey 唯一约束只有 (key, endpoint)（app/modules/idempotency/models.py:22-24），reserve/get_cached（service.py:18-50）也只按这两维；中间件用 method+path 作 endpoint（app/main.py:100）。两人用相同 key 命中同一端点时，后到者直接拿到前者缓存的响应体（如建档返回的患者数据），构成越权读取。
- 无过期/清理：created_at 无 TTL 或清理任务（全仓无清理逻辑）；processing 行在进程崩溃/客户端断开后永久残留（只有 5xx 与异常才 release，main.py:131-132），该 key 后续永远 409。
- 缓存 4xx：除 5xx 外都 store_response（main.py:131-140），400/404 用同 key 重试会永久返回旧错误（tests/test_idempotency.py:75-86 明确断言此行为）。
- 全量缓冲响应：中间件 async for chunk in response.body_iterator 后重建 Response（main.py:126-152），大响应/文件流整块进内存并丢失原始流式语义。
- 没有真实使用者：his_client 未发送 Idempotency-Key（全仓仅 tests/test_idempotency.py 使用），写接口重复提交防护实际未生效；服务端也无法知道哪些客户端支持。
- 会话借用模式脆弱：_session() 用 next(get_db()) 取会话并手工 close（service.py:14-15），生成器未被消费/关闭；覆盖：tests/test_idempotency.py 7 例（重放、无 key、endpoint 隔离、业务错误缓存、并发原子占位、409、GET 忽略）。

**标准依据：** NHC 2018-4 第112项 数据交换（⚠️：有 REST API/集成模块，缺标准交换规范与失败重试边界）；NHC 2018-4 第115项 业务规则流程管理（⚠️：有业务规则代码，缺可视化流程配置）；电子病历分级 2018-1079 第35项 基础设施与安全管控（⚠️：身份、权限、审计、备份仍需完善）

### insurance_catalog（P2 / optimize_later）

- 覆盖：tests/test_insurance_catalog.py 5 例 + tests/test_insurance_match.py 6 例（甲乙丙/歧义/未匹配/页面）；管理台 /admin/insurance-catalog 有页面（admin/router.py:667-749）与 E2E 截图脚本（scripts/e2e_insurance_admin.py），但 base.html 无该导航。

### notify（P2 / optimize_now）

通知采用 outbox（pending/sent/failed + attempts/last_error + 手工重试）方向正确；但没有任何自动派发器：审批、审方、超时升级产生的通知只能由 admin 点 POST /notifications/dispatch 或脚本触发，生产会长期滞留 pending；internal 渠道不投递也置 sent；已读状态按角色行共享；retry 无上限。审批闭环的“提醒”环节实际未闭合。

**发现：**
- 没有派发器：dispatch_pending（app/modules/notify/service.py:84-123）只能由 admin 的 POST /notifications/dispatch（router.py:54-58）触发，全仓仅 scripts/e2e_full.py:227 调用；approval.service 的 notify_role/enqueue（app/modules/approval/service.py:289-298、395-402、414-423、448-457、463-472）只入队，无定时任务消费。
- internal 渠道假送达：dispatch_pending 对 channel=="internal" 只 pass 后置 sent（service.py:96-97、114-115），没有投递凭据，状态与真实送达脱节。
- 已读状态按角色共享：inbox（service.py:126-133）按 recipient=="role:<role>" 取件，一行通知被同角色所有账号共享；mark_read（service.py:136-146）写单一 read_at → 一人已读全角色变已读。
- 状态字段语义混用：NotificationOutbox.status 同时承载 pending/sent/failed/read（models.py:21-22），mark_read 会覆盖 sent，无法统计“未送达/未读”。
- 重试无上限：retry_failed（service.py:149-158）把所有 failed 重置为 pending，不限次数、无退避，坏地址会无限重试。
- 覆盖：tests/test_clinical_refactor.py::test_approval_notifications（入队/派发/已读）、scripts/e2e_full.py；客户端有 his_client/ui/notifications.py（管理员可派发/重试），管理台无通知页面（templates 无 notifications.html）。

**标准依据：** NHC 2018-4 第20项 信息推送（⚠️）；NHC 2018-4 第49项 危急值管理（✅：危急值标记/通知/医生确认/超时基础闭环；通知渠道依赖本模块）；医院智慧服务 2019-236 第4项 信息推送（⚠️）

**参考工程：** docs/标准逐条对照.md §4.1（49）危急值管理、§二 #35 基础设施与安全管控；docs/部门工作站与审批.md（审批待办与通知入口）；reference/comparison.md 未覆盖通知

**建议：** 加定时派发（服务启动后台任务或外部 cron 调 dispatch），或把 dispatch 挂在审批动作后的事务外触发；internal 与 sent 状态解耦，拆 sent_at/read_at 两个语义；收件人改 user 维度（或 role 行+每用户 read 表）；retry 加次数上限与退避；管理台补通知列表页。

### sms（P2 / merge）

短信只有落库：send_sms 固定 status=sent，不调用任何短信服务，记录里没有 provider id/错误/重试/操作人。它在三个业务点被同步调用（检验报告、影像报告、预约成功），而 notify 另有一套 channel=sms 的 outbox（配置 sms_webhook_url 后真实 HTTP 发送、带失败重试）。同一能力两套实现，口径与记录会分裂。

**发现：**
- 只落库不外发：app/modules/sms/service.py:6-17 send_sms 直接写 SmsMessage 并固定 status="sent"；models.SmsMessage 无 provider_msg_id/error/attempts/operator（models.py:8-21），无法判断是否送达。
- 与 notify 重复：app/modules/notify/service.py:65-74 在配置 sms_webhook_url 时另建 channel="sms" 的 NotificationOutbox，由 dispatch_pending（notify/service.py:105-111）真正 POST；send_sms 记录不进 outbox、无重试，两入口产生两套记录。
- 同步阻塞业务接口：lis.service._notify_result_ready（app/modules/lis/service.py:352-371）、pacs.service._notify_result_ready（app/modules/pacs/service.py:111-129）、appointment.service.create_appointment（app/modules/appointment/service.py:64-73）在请求线程直接 send_sms；接真实网关后报告/预约 RT 被运营商绑定。
- send_sms 内部 db.commit()（service.py:15）：当前三个调用点都在业务 commit 之后，暂未破坏原子性，但这是隐式约定，后续在事务中调用会提前提交半成品。
- 无模板/频控/退订：template 为自由字符串（schemas.py:7），content 直接截断 200 字（service.py:11），phone 仅校验长度（schemas.py:5），无黑名单与频控。
- 覆盖：tests/test_sms.py 3 例、tests/test_appointment.py 断言预约短信；无客户端/管理台页面，管理台无短信记录页。

**标准依据：** NHC 2018-4 第20项 信息推送（⚠️：有 SMS 模块，未覆盖全部就诊节点）；医院智慧服务 2019-236 第4项 信息推送（3级：取药/报告/危急值告知；⚠️）；NHC 2018-4 第5项 预约签到（⚠️）与第4项 预约内容（✅，预约通知依赖短信）

**参考工程：** docs/标准逐条对照.md §三 第4项、§四 第20项；docs/入库与医保目录设计.md §十八 界面汉化（短信模板/状态标签）；reference/comparison.md 未覆盖短信

**建议：** 合并进 notify：短信作为 NotificationOutbox 的一个 channel，复用 attempts/last_error/retry/回执字段；send_sms 改为 enqueue（不 commit），由派发器统一发送；补模板注册表、频控、退订与 provider 回执号；报告/预约接口改异步入队。

**不优化理由：** 取 merge 而非优化：notify 的 outbox 已具备失败重试、渠道状态与重发入口，短信模块缺的正是这些；先在 sms 再补一套网关/重试会形成第二种可靠投递实现，合并到一个 outbox 成本更低。

reports 实质只有“科室收入”一张报表+一个 xlsx 导出（2 路由/134 行），核心 service 已被 bi/executive 与 admin 报表页复用，无独立模型与生命周期，建议并入 bi。

**发现：**
- 能力范围：app/modules/reports/router.py 仅 GET /reports/departments/revenue 与 /export.xlsx；schemas.py 仅 DepartmentRevenueItem；无独立 models.py。
- 被跨模块复用：app/modules/bi/executive.py:15 与 app/modules/admin/router.py:48 均 import department_revenue → 报表逻辑事实属 bi/公共层，reports 只是路由壳。
- 科室归属是当前值非快照：reports/service.py:33-36 经 Registration→Doctor→Department 取 Doctor.department_id，EncounterCharge 无科室字段 → 医生调科后历史报表金额漂移，口径不可复现。
- 退费口径同病：service.py:61-71 只认 status=='refunded'（漏 partially_refunded）；refunded_amount 用 EncounterCharge.amount 而非实退金额，refunded_quantity 未参与（app/modules/charges/models.py 有该字段）。
- 全量内存聚合：service.py:24-71 先 query.all() 再 Python 求和，无 SQL group by。
- 口径已固化进测试：tests/test_reports.py:64-68 断言内科 paid_amount=10+20+25、drug_amount=25 等具体数字，调整口径需同步改断言。
- 鉴权：两条路由均 require_role('admin')（router.py:22,32），director/cashier 不可读；his_client/api.py 无 /reports/。
- 测试：tests/test_reports.py(3) 覆盖两科室归类/日期过滤/权限；tests/test_report_export.py:62-83 覆盖 xlsx 与权限；未覆盖调科漂移、部分退费、大数据量。

**标准依据：** NHC-2018-4 第(74)项 财务信息管理（报表维度不足）；EMR-2018-1079 第38项 信息利用/医疗质量控制；智慧服务-2019-236 第17项 基础与安全/服务监督

**参考工程：** reference/comparison.md §1 上海哲策独立 his-module-report 与当前 2 路由报表的规模差；reference/comparison.md §3.6 字段级对照（第三方按处方头/发药明细出报表）

**建议：** 并入 bi：department_revenue 移入 bi/service 或 bi/revenue.py，/reports/* 保留为兼容别名；在 bi 补科室维度快照（结算时写 department_id 或单独归集表）。

**不优化理由：** 合并不立即优化的理由：模块本身不产生错误结果（仅口径与 finance 相同待修），合并属结构性整理；在 finance/bi 口径统一时顺带搬移，可避免现在为目录好看做一次无收益的引用点改动。
