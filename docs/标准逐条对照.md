## 一、审计方法与边界

### 1.1 使用的原始材料

- [《全国医院信息化建设标准与规范（试行）》（国卫办规划发〔2018〕4号）](https://www.nmgyyxh.org.cn/nmgyyxh/zcfg/686cdcc2f266ba2c90c83a77.shtml)：PDF 5.1 MB，22 类 262 项。
- [《电子病历系统应用水平分级评价标准（试行）》（国卫办医函〔2018〕1079号）](https://niha.org.cn/prod-api/web/news/noticeDetail/329)：PDF 文本中的 0–8 级、39 个评价项目。
- [《医院智慧服务分级评估标准体系（试行）》（国卫办医函〔2019〕236号）](https://wjw.fujian.gov.cn/xxgk/zfxxgkzl/zfxxgkml/wszh/yzgl/201904/t20190430_4861177.htm)：5 类 17 个评估项目。
- [OpenHIS 信创版](https://gitee.com/tntlinking-opensource/openhis-itai)：仅参考模块边界和产品结构，不复制代码。

### 1.2 判断规则

- **✅ 已具备**：代码中存在对应模型/接口/页面，且主要流程可执行。
- **⚠️ 部分具备**：有字段/页面/局部流程，但缺少标准要求的闭环、状态、审计或共享。
- **❌ 缺失**：没有对应能力，不能靠“以后接接口”算已具备。
- **— 不适用**：机房、硬件、网络、后勤设备等非本软件交付范围；或当前明确不做住院/手术/ICU。

### 1.3 不能从本审计直接得出的结论

本审计**不**给出“电子病历 X 级”“智慧服务 X 级”的正式结论。原因：

- 评级要计算功能分 × 有效应用范围 × 数据质量；
- 需要医院实际应用比例、数据质量抽样、技术基础环境；
- 当前系统定位是小型门诊，不能把三级医院要求直接套成必做项。

### 2.1 关键结论

- 门诊核心（10–15）大体在 **2–3 级之间**：有电子处方、检验/检查申请与报告、结构化门诊病历。
- 真正卡住 3/4 级的不是“有没有页面”，而是：
  1. **处方头缺失**：`PrescriptionItem` 直接挂 `encounter_id`，无法按处方审方/上传/追溯。
  2. **病历修改痕迹缺失**：签名后锁定，但签名前的修改没有版本表；4 级以上要求可追溯。
  3. **药事审方缺失**：有发药和取药码，没有“待审方→通过/退回→调配→发药”的状态机。
  4. **执行闭环缺失**：注射/输液执行单未从处方明细派生；`Dispense` 没有实际发药明细。
  5. **数据共享是接口级而非平台级**：有 FastAPI/集成模块，但没有统一主数据、患者主索引合并、访问审计。

### 3.1 当前可务实争取的目标

不建议直接冲 4/5 级。先做到 2 级中“院内智慧服务初步建立”的几个基础项：

- 诊前：预约、实名认证、号源/停诊通知；
- 诊中：费用/报告/取药状态查询；
- 诊后：满意度/随访；
- 全程：移动支付；
- 安全：统一身份认证。

这些和当前 `appointment/registration/portal/kiosk/sms/payment_gateway` 能自然衔接，不需要重做系统。

标准要求 8 项功能、4 个知识库、8 项病历内容、3 种录入方式、3 种数据格式。当前：

- 有主诉、现病史、既往史、个人史、婚育史、家族史、体格检查、辅助检查、处理意见；
- 有诊断编码+名称，但字典只有常用项，不是完整 ICD-10；
- 有模板/质控雏形，但没有诊断鉴别库、医学术语库、病历质控规则库；
- 没有语音录入、图形图像数据格式。

结论：**⚠️ 部分**。二级医院要求的“4 项功能、6 项内容、1 种录入、2 种格式”大致接近；三级医院要求仍有明显差距。

#### （23）门急诊处方和处置管理

标准要求处方/处置录入、审核、分析 3 项功能，支持门诊、急诊、检查、检验、治疗、手术 6 种类型，提供药物/检验检查/手术治疗/合理用药/医保控费 5 种知识库。当前：

- 处方、检验、检查、治疗有入口；
- 没有处方头、没有处方级审核/分析；
- 手术/急诊未形成完整门诊闭环；
- 医保控费是 Mock/规则雏形，不是知识库。

结论：**⚠️ 部分**，且处方头是 P0。

#### （24）门诊合理用药

标准要求自动复核、实时提醒、在线查询、用药提示、统计分析、知识库 6 项功能，以及相互作用、配伍禁忌、适应症 3 类提醒。当前：

- 有过敏硬拦截、同药重复、部分相互作用、特殊级抗菌药拦截；
- 有医保事前提醒 Mock；
- 没有处方点评、剂量/肾功能/儿童/老年校验、统计分析、完整知识库。

结论：**⚠️ 部分**；不能宣称达到三级医院要求。

#### （29）非药品医嘱执行

标准要求身份确认、临床信息共享、医嘱核对、标本管理、执行确认、结果反馈、审核知识库 7 项功能，支持条码/二维码/RFID。当前：

- 检验有标本/采集/签收/拒收；
- 治疗有开立/执行状态；
- 没有统一“非药品医嘱执行”对象，没有腕带/扫码/RFID 闭环。

结论：**⚠️/❌**，需新增执行单模型或统一医嘱执行表。

#### （30）药品医嘱执行

标准要求配药、标签、患者身份查对、药品查对、患者呼叫、患者/医嘱自动获取比对、配伍禁忌审查、用药前后病情获取 8 项功能。当前：

- 有发药、取药码、发药人/取药人、签名；
- 没有住院药品配置、没有患者身份扫码核对、没有配药标签/呼叫闭环；
- 高危药品只有标识和护理双人核对基础。

结论：**⚠️**，门诊发药可用，但达不到条款的完整执行闭环。

#### （35）临床检验信息管理

标准要求申请、标本、结果、报告、危急值、质控、仪器接口等。当前：

- 有 LabItem/LabRequest、标本号、采集/签收/拒收/检验/报告/审核、参考范围、异常标记、危急值登记/医生确认；
- 没有仪器接口、质控、条码打印、年龄/性别参考区间。

结论：**✅/⚠️**，门诊检验主线可用，离 4 级“全院共享 + 决策支持”仍有差距。

#### （36）医学影像信息管理

标准要求申请、预约、检查、报告、图像、PACS 关联。当前：

- 有 ImagingItem/ImagingRequest、accession_no、报告文本、image_url；
- 没有真实 PACS 接口、图像调阅、检查排期/预约、结构化报告。

结论：**⚠️**，不能把 `image_url` 当成 PACS 已接入。

#### （46）电子病历质量管理

标准要求质控规则库、环节质控、终末质控、整改闭环。当前：

- 有五项必填评分（60 分及格）；
- 没有规则库、没有整改任务、没有科室/医生维度统计。

结论：**⚠️**，只是“表单完整性检查”，不是完整病历质控。

#### （49）危急值管理

标准要求危急值识别、报告、通知、接收、处理、超时升级、记录。当前：

- 检验可标危急值、通知对象/时间、医生确认/备注、超时 30 分钟标记；
- 没有短信/电话自动升级、没有按科室/人员分级通知。

结论：**✅/⚠️**，基础闭环有，升级机制不足。

#### （51）（52）（53）药事、处方点评、发药

- 有药房、库存、发药/退药、取药码；
- 没有独立药师审方、处方点评、发药明细；
- 没有“处方状态/审方人/审方时间/退回原因”。

结论：**⚠️**，是当前 P0 的最大缺口之一。

#### （73）业务结算与收费

标准要求收费、结算、医保、财务对账。当前：

- 有收费/退费/发票/混合支付；
- 医保是 Mock，患者 `insurance_type` 没有进入结算；
- 没有起付线/封顶线/目录限定支付/日对账。

结论：**⚠️**，真实医保部署前不能宣称合规。

#### （108）–（112）信息平台

- 有字典/主数据雏形、患者主索引字段、REST API；
- 没有统一主数据注册、EMPI 合并、标准共享文档、平台级数据交换；
- 没有单点登录、服务监控、数据质量评价。

结论：**⚠️/❌**，当前是“应用系统 + 接口”，不是医院信息平台。

### 4.2 262 项统计（软件初筛）

按当前表统计：

```text
第 1–123 项（软件/业务相关）：
✅ 3 项
⚠️ 53 项
❌ 45 项
— 22 项（当前明确不做或非软件范围）

第 124–262 项（机房/硬件/网络/安全/新兴技术）：
```

这组数字不能当“得分”，但能说明一个事实：

- 当前系统不是“大面积空白”；
- 大量项目是**部分具备**，差在闭环、审计、共享；
- 真正空白集中在患者移动端、区域协同、住院/手术、后勤/科研教学、平台治理。

## 六、按标准的整改建议（含验收标准）

### P0-1 处方头与处方类型

对应标准：

- NHC（23）处方和处置管理、（24）合理用药、（52）处方点评；
- EMR 03.01 处方书写 3/4 级；
- 智慧服务 9 药品调剂与配送。

实施：

```text
prescriptions
- id / encounter_id / prescription_no / type / status
- prescribed_by / reviewed_by / reviewed_at
- insurance_upload_status
prescription_items.prescription_id
```

类型：

```text
western / tcm_herb / narcotic / special
```

验收：

- 一张西药/中成药处方最多 5 种，按处方头计数；
- 删除/作废按处方头，不按单个 item；
- 打印/医保上传能拿到处方号；
- 现有 `PrescriptionItem` 数据迁移后不丢。

### P0-2 药师审方状态机

对应：

- NHC（51）（52）（53）；
- EMR 29 门诊药品调剂；
- 智慧服务 9。

状态：

```text
draft → pending_review → approved / rejected → dispensing → dispensed
```

验收：

- 医生提交后不能直接发药；
- 药师可退回并填写原因；
- 发药记录关联审方人/时间；
- 审方未通过不能生成发药凭证。

### P0-3 病历修改留痕

对应：

- NHC（22）（46）；
- EMR 03.06 门诊病历 3/4 级；
- 电子病历应用管理规范。

实施：

```text
medical_record_versions
- record_id / version / changed_by / changed_at / before_json / after_json
```

验收：

- 签名前每次修改有版本；
- 签名后不可改，只能新增补充记录；
- 能查到谁在何时改了哪些字段。

### P0-4 患者访问审计

对应：

- NHC 安全防护/平台服务；
- EMR 35 基础设施与安全管控；
- 智慧服务 16 安全管理。

验收：

- 记录 `username / patient_id / action(view/edit) / at / ip`；
- 医生查看历史、护士查看患者、收费查看费用都留痕；
- 审计日志不可由普通业务角色删除。

### P1-1 实际发药明细

对应 NHC（30）（53）、EMR 29。

```text
dispense_items
- dispense_id / prescription_item_id / quantity / batch_no
```

验收：取药凭证只显示本次实际发放，不显示未发/退药。

### P1-2 注射/输液执行单

对应 NHC（29）（31）（32）、EMR 8/23。

验收：处方明细 route=静滴/肌注 → 派生执行单；执行单有患者、药品、剂量、批号、执行人、时间、核对人。

### P1-3 LIS/PACS 接口

对应 EMR 11–14、16–22；NHC（35）（36）。

验收：

- 检验申请/标本/结果/报告/危急值可双向；
- 影像申请/报告/图像可调阅；
- 失败可重试，接口有审计；
- 不把 `image_url` 当作 PACS 已接入。

### P1-4 医保患者类型进入结算

对应 NHC（73）、智慧服务 12。

验收：

- `insurance_type` 参与结算；
- 有起付线/封顶线/目录限定支付的接口位；
- Mock 与真实接口明确区分，不宣称已接入。

### P2 智慧服务

按 17 项中当前最薄弱的：

1. 患者移动端（预约、报告、费用、取药状态）
2. 满意度/投诉
3. 随访
4. 院内导航/智能导医
5. 统一身份认证/SSO

这些是 P2，不应先于处方头和审方。

## 八、审计结论

当前系统不是“没有模块”，而是：

```text
门诊流程完整
临床证据链偏薄
评级条款的闭环/审计/共享不足
```

最接近的务实目标是：

1. 先把门诊处方头和药师审方做成闭环；
2. 再把病历修改留痕和患者访问审计补上；
3. 然后做实际发药明细、注射执行单、LIS/PACS 接口；
4. 最后才做智慧服务移动端。
