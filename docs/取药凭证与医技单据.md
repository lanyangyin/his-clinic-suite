# 取药凭证与医技单据边界

## 取药凭证

取药凭证是聚合视图，不是新处方，也不是费用明细的替代品。

### 接口

```http
GET /pharmacy/dispense-slips/{encounter_id}
```

返回只读 JSON：

```text
患者身份（姓名脱敏、性别、年龄、患者号）
就诊标识（encounter_id、registration_id）
科室、接诊医生
结算时间、打印时间、有效日期
药房、窗口、取药号、当前等待人数
处方张数
临床诊断
本次实际发药明细
中药处方摘要
医师/调配药师/核对药师/取药人
提示
```

### 打印

```http
GET /print/dispense-slip/{encounter_id}
```

A5 风格只读凭证，包含：

- 身份与就诊
- 取药指引
- 临床诊断
- 药品明细
- 签名栏
- 重要提示

### 药房客户端

发药成功后，药房工作站新增：

```text
打印取药凭证
```

位置在“打印上次发药袋标签”旁边。点击后打开内嵌打印预览，可打印、导出 PDF 或转到浏览器。

### 数据来源

| 内容 | 来源 |
|---|---|
| 患者 | Patient |
| 就诊/诊断 | Encounter / EncounterDiagnosis |
| 科室/医生 | Department / Doctor |
| 药品明细 | PrescriptionItem |
| 中药处方 | TcmPrescription |
| 发药状态/签名 | Dispense |
| 窗口/取药号/等待 | PharmacyCall / PharmacyPickupCode |
| 结算时间 | Payment |

没有为凭证单独复制一套患者/药品数据，避免打印后又产生第二份真相。

### 发药队列

现有模型已经有独立队列实体：

```text
PharmacyCall
- encounter_id
- queue_no
- window_no
- status
- called_at

PharmacyPickupCode
- encounter_id
- code
- used_at
```

凭证里的窗口号、取药号、等待人数是实时聚合值，不写回处方。

### 重要限制

当前 `Dispense` 是“一次就诊一次发药”，没有按药品明细记录实际发药数量。  
因此凭证的药品明细来自本次就诊处方，并只在 `Dispense.status=dispensed` 后允许打印；如果未来要支持部分发药/缺药替代，应增加：

```text
dispense_items
- dispense_id
- prescription_item_id
- quantity
- batch_no
```

## 检查与检验

现有系统已经是两套独立模型，不是 `ExamRequest(type=...)`：

### 检查

```text
ImagingItem
- code
- name
- body_part
- price

ImagingRequest
- encounter_id
- item_id
- accession_no
- status（pending / reported）
- report / image_url
```

下游是 PACS/RIS。

### 检验

```text
LabItem
- code
- name
- specimen_type
- reference_low/high
- result_kind

LabRequest
- encounter_id
- item_id
- status（pending / collected / received / testing / reported / reviewed / rejected）
- specimen_no
- result_value / result_unit
- critical_flag
```

下游是 LIS。

### 结算

两者都通过：

```text
encounter_id
```

汇入 `EncounterCharge`，财务视图合并，执行视图分离。

### 当前缺口

- `ImagingItem` 没有显式 `modality` 字段，目前靠名称区分 MRI/CT/XR。
- `LabItem` 没有显式 `test_panel` 字段，目前靠项目名称/收费项目表达组套。
- 检查状态机目前只有 `pending/reported`，比检验的采样、签收、审核链路短。

这些是后续数据模型增强，不应该用一个混合 `ExamRequest` 来解决。
